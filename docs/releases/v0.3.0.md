# v0.3.0 — Custom content types

Date: 2026-08-15

Third tagged release of Tycoma. It ships the **Custom Content Types** epic on top of the admin
dashboard and the public site: the admin can define content types with a fixed field set, manage
entries for them, and render published entries on the public site — without leaving the existing
hexagonal `content` module.

## Highlights

- **Content type definitions** — `ContentType` model (name, slug, description, JSON `fields` list)
  with the fixed field kinds `text`, `longtext`, `number`, `boolean`, `date`. A field-coercer
  registry (`FIELD_COERCERS` in `src/modules/content/domain/content-type-fields.ts`) gives one
  strategy per kind; unknown field names are dropped, required fields are enforced.
- **Entries** — `ContentEntry` model with per-type slug, title, status
  (`draft`/`scheduled`/`published`), `publishedAt`, `scheduledAt`, and JSON `fields` validated
  against the type definition. Unique per `(contentTypeId, slug)`.
- **Admin UI** at `/admin/content-types` — list, new/edit type (dynamic field editor with
  add/remove rows), entries list/new/edit per type, publish + delete actions. Server Actions in
  `src/app/admin/_actions/content-types.ts` with Zod-validated form payloads.
- **Public reading** at `/types/[type]` (index of published entries) and `/types/[type]/[slug]`
  (detail) with `generateMetadata`, canonical URL, and a generic field renderer. Drafts and
  missing slugs hit `notFound()`.
- **Use cases** in `src/modules/content/application/use-cases/content-types.ts`:
  list/get/save/delete content types; list/get/create/update/publish/delete entries; plus the
  two public reads (`listPublishedEntriesByTypeSlug`, `getPublishedEntryByTypeAndSlug`). Audit
  events recorded for every mutation through the existing `AuditEventWriter` port.
- **Repository ports** (`ContentTypeRepository`, `ContentEntryReader` / `ContentEntryWriter`)
  split per ISP convention; Prisma adapter with explicit `toDomain` / `toPersistence` mappers.

## Architecture notes

- The new logic lives entirely inside the existing `content` module — no new module, no new
  public surface for other modules to depend on. `domain/` stays framework-free; `application/`
  mocks the ports in tests; `infrastructure/` owns the Prisma adapter.
- The framework composition root (`src/app/_lib/modules.ts`) was left untouched: the new use
  cases were wired inside `content/application/index.ts` next to the existing public reads.
- Audit events follow the established pattern: every mutation (`content.type_*`,
  `content.entry_*`) flows through the `AuditEventWriter` port.
- The public site keeps its hexagonal contract: `src/app/(site)/types/**` is composition-only,
  calling the published-only reads (`listPublishedEntriesByTypeSlug`,
  `getPublishedEntryByTypeAndSlug`) through `content`. Drafts never leak.
- New `docs/testing-playbook.md` documents the testing pyramid (no mocks in domain,
  port-only mocks in application), the smoke checklist, and the regression gate.

## URL scheme

| Entity             | Route                              |
| ------------------ | ---------------------------------- |
| Content type index | `/types/[type]`                    |
| Content entry      | `/types/[type]/[slug]`             |

Reserved static segment `types` takes precedence over the page detail `[slug]` (same shadowing
rule already documented for `posts`/`categories`/`tags`).
